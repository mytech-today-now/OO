Privileged profile integrity and Windows privacy state

Failure mode

The installer validates the profile bytes and manifest, compares their digests with the approved values, and later passes the profile path to O&O. O&O opens that path after the PowerShell check. If a lower-privileged process can write the package directory during that interval, it can replace the file after validation but before the native process reads it. The code's digest check protects against a changed file observed during validation, but a path-based handoff leaves a check-to-use interval. This report has not established that the current launch environment exposes such a writable path, so exploitability is a Testable assumption.

Evidence or rationale

Install-OOShutUp10.ps1, Get-OOShutUpApprovedProfile around lines 914-1114, reads and hashes the manifest and cfg, then returns the cfg path. Invoke-OOShutUpConfiguration around lines 1355-1380 reloads and validates the pair, checks the approved digest, and invokes Start-Process with that path. The process is asked to open the file later. The script's Test-SystemTaskTargetAcl check begins around line 1647 and is used during task setup after initial O&O configuration; it does not establish that the source profile directory was protected before that first configuration. No checked-in profile exists to exercise this boundary.

Testable assumption: A lower-privileged process can write the source package directory during an elevated run and can alter the cfg in the short interval before O&O opens it. Confirm or disprove this with two test accounts and a barrier-controlled swap in a disposable VM.

Why this matters

A profile is the exact input that selects privacy changes. If an elevated process applies different bytes from those the operator reviewed, the approval screen and the operation no longer describe the same change. Hashes in the task prevent later profile drift only when they are checked at the time of use; they cannot make an already-open-by-path handoff atomic. The risk becomes especially serious when an administrator is asked to run a package located in another account's writable directory.

Recommended mitigation

Create a protected, per-run profile snapshot in a directory whose ACL is verified for SYSTEM and Administrators, copy both files with exclusive creation, verify the exact approved hashes on the destination, and give O&O only that snapshot path. Hold the snapshot stable until the child process exits, then remove it only after confirming cleanup. If the source or destination cannot be secured or reverified, stop before O&O starts and report that no settings were applied. Do not treat a second hash read as a complete fix if an untrusted writer can still alter the file after the read.

Fallback copy: The approved profile changed after validation. No O&O process was started; restore the reviewed profile and retry.
